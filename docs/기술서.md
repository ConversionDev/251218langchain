## 3. 시스템 아키텍처

- **클라이언트** → FastAPI(CORS) → `/api/*`(REST), `/internal/*`(LLM 프록시), `/mcp`(MCP)
- **도메인**: `domain.hub.orchestrators`(chat, spam, graph, disclosure), `domain.hub.repositories`, `domain.hub.llm`
- **데이터**: PostgreSQL + pgvector(임베딩), Alembic 마이그레이션

### 3.1 스타 토폴로지 (Hub-Spoke)

중앙 **Hub**가 요청을 받아 도메인별 **Spoke(MCP)** 로만 위임하는 구조입니다. Hub는 무거운 모델(ExaOne·LLaMA)을 직접 로드하지 않고, 각 MCP가 자신의 Spoke URL로 `call_tool` 하며, Spoke가 필요 시 Hub의 내부 API(`/internal/llama`, `/internal/exaone`)를 호출합니다.

```
                        [ 클라이언트 ]
                              │
                              ▼
                   [ FastAPI 게이트웨이 ]
                     /api/*  /mcp  /internal/*
                              │
                              ▼
              ┌────────────────────────────────┐
              │     Hub (Central Control)       │
              │   /mcp  FastMCP · call_tool     │
              │   요청을 Chat/Spam MCP로 위임    │
              └────────────────────────────────┘
                        │              │
              ┌─────────┘              └─────────┐
              ▼                                   ▼
     ┌─────────────────┐                 ┌─────────────────┐
     │   Chat MCP      │                 │   Spam MCP      │
     │ /internal/mcp/  │                 │ (별도 9021 등)  │
     │ chat, chat-spoke│                 │ 이메일·스팸 분류 │
     └────────┬────────┘                 └────────┬────────┘
              │                                     │
              ▼                                     ▼
     ┌─────────────────┐                 ┌─────────────────┐
     │  Chat Spoke     │                 │  Spam Spoke     │
     │ ExaOne 채팅 등  │                 │ LLaMA 스팸 분류 │
     └────────┬────────┘                 └────────┬────────┘
              │                                     │
              └──────────────┬──────────────────────┘
                             ▼
                   [ Hub 내부 API ]
                   /internal/llama
                   /internal/exaone
                             │
                             ▼
                   [ PostgreSQL · pgvector ]
```

| 구성요소 | 역할 |
|----------|------|
| **Hub** | `/mcp`에 마운트. 들어온 요청을 Chat MCP / Spam MCP로만 라우팅. 모델 직접 로드 없음. |
| **Chat MCP / Spoke** | 동일 프로세스(`/internal/mcp/chat`, `chat-spoke`). 채팅·RAG는 ExaOne. Spoke가 Hub의 ExaOne API 호출. |
| **Spam MCP / Spoke** | 이메일 분석·스팸 분류. Spoke가 Hub의 LLaMA API 호출. (별도 포트 9021/9022 예시 가능) |

상세: [backend.md](backend.md) §아키텍처, §8 MCP (Hub-Spoke).

## 6. 성능·비용·리소스·UX 개선 (작성 참고용)

이력서·제안서에 넣을 때 참고할 수 있도록, **코드에서 구현된** 내용을 정리했습니다.

### 6.1 시간 감소

| 구현 | 위치·설명 |
|------|-----------|
| **임베딩 배치 처리** | 직원 임베딩 일괄 갱신 시 `embed_documents(batch)`로 배치 단위 처리. 배치 크기 32·512 등으로 API 호출·처리 횟수 감소. (`employee_repository.fill_embeddings_for_employees`, `domain/shared/embedding.py`) |
| **채팅 스트리밍** | 답변을 전체 생성 후 한 번에 보내지 않고 **스트리밍(SSE)**으로 전달. 첫 토큰까지 대기 시간 단축, 체감 응답 속도 개선. (`chat_orchestrator.run_agent_stream`, `/api/agent/chat/stream`) |
| **이력서 분석 캐시** | 동일 파일 재업로드 시 **세션 캐시**에서 즉시 반환. API 재호출 없이 폼 채우기 반복 시 시간·부하 절감. (`resumeToBaseline.tsx` `getCachedResumeResult`, `apply/page.tsx`) |

### 6.2 인프라 비용 절감

| 구현 | 위치·설명 |
|------|-----------|
| **Lazy 로딩(스타트업)** | 서버 기동 시 DB만 확인하고, **ExaOne·Embedding·FAISS·스팸 LLaMA**는 **첫 요청 시** 로드. t3.small 등 소형 인스턴스에서 메모리 부담·OOM 위험 감소, 불필요한 상시 로드 비용 절감. (`fastapi_server.init_v1`, `project.md` §배포) |
| **FAISS 미로드, pgvector만 사용** | RAG 검색은 스타트업에서 FAISS 인덱스를 로드하지 않고 **pgvector(HNSW)** 만 사용. 메모리 사용량·인프라 스펙 요구 완화. (`ensure_rag_initialized`, `employee_repository.search_employees_with_filter`) |

### 6.3 리소스 절감

| 구현 | 위치·설명 |
|------|-----------|
| **임베딩 모델 싱글톤·캐시** | 동일 설정으로 `get_embedding_model` / `get_disclosure_embedding_model` 호출 시 **캐시된 인스턴스** 반환. 모델 중복 로드 방지, GPU/메모리 사용 절감. (`domain/shared/embedding.py` `_embedding_model_cache`) |
| **ExaOne/LLM 추론 후 GPU 캐시 정리** | 생성 직후 `torch.cuda.empty_cache()` 호출. OOM 방지·다음 요청을 위한 메모리 확보. (`exaone_model.py`, `strategy.md` §도구·GPU) |
| **스팸 분류 배치 처리** | LLaMA 스팸 분류를 `classify_spam_batch(batch_size=32)` 등으로 배치 호출. 요청당 오버헤드·리소스 사용 효율화. (`llama_classifier.predict_batch`, `ambiguous_case_filter`) |

### 6.4 사용자 경험 개선: 로딩·체감 속도

| 구현 | 위치·설명 |
|------|-----------|
| **채팅 스트리밍** | 답변을 실시간으로 표시해 **첫 글자까지 대기 시간**을 줄이고, 긴 답변도 끊김 없이 보여줌. (`/api/agent/chat/stream`, 프론트 `chat/services.ts`) |
| **이력서 분석 캐시** | 동일 파일 재선택 시 **저장된 분석 결과**를 즉시 폼에 반영. 재분석·로딩 없이 체감 로딩 시간 제거. (`getCachedResumeResult`, `cachedLoaded` 토스트) |
| **페이지네이션** | 직원·신입 목록을 **페이지 단위(예: 20건)** 로 조회. 한 번에 전체를 불러오지 않아 초기 로딩·응답 시간 단축. (`core/employees`, `core/new-hires` `PAGE_SIZE`) |
| **로딩 상태 표시** | 목록·업로드·임베딩 갱신 등에 **로딩 UI** 적용. 진행 중임을 명확히 표시해 대기 체감 개선. (각 페이지 `loading` state, 버튼 `disabled`) |

# ESG 전력·손실량·폐기물 — 데이터셋 규모 및 활용 방안

**문서 갱신(구현 동기화)**: 2025-03 — 시계열 키 `noticedate`+`hour`, `measurements`에 포함되는 이상(CONTRACT만), 다변량 5종·비율, scrap/waste README 자동 반영을 코드와 맞춤.

손실량(scrap)·산출 폐기물(waste)까지 포함한 **의미 있는 데이터셋**을 **어느 정도 규모로** 만들고, **지금 구현된/추가할 코드에서 어떻게 쓸지** 정리한 문서.

**목적**: **시계열**, **이상치**, **예측**까지 고려해 **최대한 의미 있는** 데이터셋을 만드는 것. 기준·참고치는 `app/data/env_mapping` 의 README·통상 참고치·전력수요/전기요금표 등을 사용해 생성 로직에 반영.

---

## 0. 시계열·이상치·예측을 위한 “의미 있는” 데이터셋 요건

데이터셋이 **시계열 / 이상치 / 예측** 세 가지에 모두 쓰이려면 아래를 만족하도록 설계한다.

### 0.1 시계열에 의미 있게

| 요건 | 설계 반영 |
|------|-----------|
| **충분한 길이** | **24개월**(2년) 권장. 추세·YoY 비교·계절 분해(일/주/연 주기)에 최소 12개월, 여유 있게 24개월. |
| **일정한 시간 간격** | **1시간** 단위: `noticedate`(일) + **`hour`(1~24)**. 시계열·Rule 3(동일 시간대 합계)·이동평균에 둘 다 사용. |
| **주기·패턴** | **shift**(day/night)에 따른 usage/production 차이, **주말/공휴일** production 0·usage 기저만, **계절성**(여름 7~8월·겨울 12~1월 usage 소폭 상승)을 생성 로직에 넣어 **추세·주기**가 드러나게 함. |
| **공정·라인별 시계열** | (process, line) 조합별로 독립 시계열이 쌓이게 해 **공정별·라인별** 추세·비교 분석 가능. |
| **다변량 시계열** | usage, production, equipment_ct, scrap, waste가 **같은 noticedate**에 함께 있으므로 **다변량 시계열** 분석·상관 구조 학습 가능. |

### 0.2 이상치에 의미 있게

| 요건 | 설계 반영 |
|------|-----------|
| **Rule 기반 이상** | 6가지 Rule에 **1:1 대응**하는 위반 행 + **validation 로그**(error_type, value, threshold)를 함께 생성 → Rule 엔진 검증·학습 라벨. |
| **다변량 이상** | Rule 단독 라벨과 구분되는 **`MULTIVARIATE_*` 5종**. 이상 슬롯 중 기본 **약 35%**가 다변량(기본 `--anomaly-rate 0.06`이면 전 슬롯 대략 **~2.1%**). **`measurements`에는 미포함**, `validation_logs`·`labeled_slots`에만 기록. |
| **라벨·메타** | 정상/이상 구분, **error_type**(Rule 위반 시), **원인 후보 ID**(규칙 테이블과 연동 가능)를 메타 또는 validation과 연결해 **지도·준지도 학습**에 사용. |
| **심각도·비율** | Rule별 0.5~1%, 다변량만 2~4%로 **이상 비율**을 현실에 가깝게 두어, 불균형 대응·정밀도/재현율 평가가 의미 있게 됨. |

### 0.3 예측에 의미 있게

| 요건 | 설계 반영 |
|------|-----------|
| **연속된 정상 구간** | 정상 92~95%로 **긴 연속 정상 구간**이 많아, **usage / production / 설비 가동** 등 **시계열 예측** 학습에 쓸 수 있음. |
| **계절·트렌드 포함** | 계절성·shift 패턴이 들어가 있어 **다음 1시간/1일/1주** 예측 모델(ARIMA, Prophet, LSTM 등) 학습에 적합. |
| **예측 대비 이탈 시나리오(선택)** | “특정 구간만 실제값을 예측값에서 크게 이탈시킨” 행을 소량 넣으면, 추후 **예측 오차 기반 이상치** Rule(예: Rule 7) 확장·검증에 사용 가능. |
| **공정·라인·시간대별** | (process, line), shift별로 나누어 **공정별·시간대별 전력 수요 예측**을 학습·평가할 수 있는 구조. |

### 0.4 기준 데이터 소스 (`app/data/env_mapping`)

- **정상 범위·설비 정격·Rule 임계치**: `README_ESG_Rule_및_설비기준.md`, `esg-dummy-data-strategy.md` 프로파일.
- **손실량·산출 폐기물 통상 참고치**: `README_배터리_손실량_폐기물_통상참고치.md` §3.2 표 → `run_generate_measurements.build_profile()`이 파싱해 `profile.json`의 라인별 `scrap`/`waste` 구간으로 반영.
- **전력 수요·요금·계약**: 전력수요 CSV, 전기요금표 PDF, 수요관리 CSV → shift baseline·계약 상한·Rule 6 참고.
- 생성 스크립트는 위 경로의 설정·문서를 읽어 **일관된 기준**으로 시계열·이상치·예측에 쓸 수 있는 한 덩어리 데이터셋을 만든다.

## 1. 데이터셋 규모 제안

### 1.1 단위·기간

| 항목 | 권장값 | 이유 |
|------|--------|------|
| **시간 단위** | 1시간 — `noticedate` + **`hour`(1~24)** | Rule 3(동일 시간대 합계), shift(day/night), 시계열·이동평균에 적당 |
| **기간** | **12~24개월** (예: 2024-01 ~ 2025-12) | YoY 비교, 계절성(여름/겨울 usage), 학습·클러스터링에 충분한 시점 수 |
| **공정·라인** | 5 process × 2 line = **10 (process, line)** | `esg-dummy-data-strategy.md` 프로파일과 동일 |

### 1.2 행 수

- **슬롯 수(공정·라인×시간)**: 1시간당 10행 → 24×365×10 = **87,600슬롯/년**. 2년이면 **약 17.5만 슬롯**.
- **measurements.csv 행 수**: 위 슬롯 중 **정상으로 나온 행** + **Rule 3(CONTRACT_EXCEED)** 로 표시된 시간대의 **10행(전 라인)** 만 CSV에 들어감. 단일 Rule·다변량 이상 슬롯은 **CSV에 없고** `validation_logs`(·`labeled_slots`)만 증가.

| 구분 | 비율(의도·기본 `anomaly-rate=0.06` 기준) | 비고 |
|------|------------------------------------------|------|
| **정상 슬롯** | 대략 **94% 전후** | `measurements`에 기록 |
| **그 외 이상 슬롯** | 대략 **6%** (라인·시간 슬롯당, CONTRACT 시간대 제외 시 `elif`) | 시간대 Rule3는 `anomaly_rate×0.15`로 **해당 시각 전 라인**이 CONTRACT 패턴; 그 외 이상은 라인별 6% 중 다변량 **35%** / 단일 Rule **65%** |
| **다변량(`MULTIVARIATE_*` 5종)** | 전 슬롯 기준 대략 **`(1−0.009)×0.06×0.35 ≈ 2.1%`** (기본값 기준) | **measurements 미포함** |
| **단일 Rule 1·2·4·5·6** | 나머지 이상 슬롯 | **measurements 미포함** |

**measurements 규모 (1년)**  
- 정상 ~82k행 + CONTRACT로 추가되는 행(시간대 수×10, 대략 수백~수천) → **대부분 시나리오에서 여전히 약 8만 대후반~9만 행/년**.  
- **2년이면 17만~18만 행** 수준 유지. 이상 전체(검증 로그)는 슬롯의 ~6%에 해당하는 건수가 별도로 쌓임.

### 1.3 손실량(scrap)·산출 폐기물(waste)

- **모든 행**에 `scrap`, `waste` 컬럼 포함.
- **정상·CONTRACT 행**: `profile.json`의 공정별 `scrap`/`waste` 구간(README §3.2×production 밴드)에서 샘플링.
- **다변량 `SCRAP_WASTE_DEVIATION`**: 프로파일 상한 대비 scrap·waste를 **약 1.12~1.38 / 1.10~1.32배**로 올림(validation·라벨 전용; measurements 미포함).

## 3. 지금 구현된 코드와의 연계 (활용 방안)

### 3.1 데이터 생성

- **구현됨**: `app/training/pipelines/esg_dummy/run_generate_measurements.py` (`cd app` 후 `python -m training.pipelines.esg_dummy.run_generate_measurements`).
- 참조: `docs/esg-dummy-data-strategy.md`, `training/pipelines/esg_dummy/README.md`(다변량 5종·출력 구분).
- 기준치: `env_mapping/README_*.md`, 손실·폐기 **`README_배터리_손실량_폐기물_통상참고치.md` §3.2 자동 반영**.

### 3.2 Rule 엔진 (6가지 Rule)

- **입력**: 한 행(또는 엑셀 업로드 행) — usage, production, equipment_ct, shift, noticedate, **hour**, process, line, scrap, waste.
- **출력**: 통과 시 → measurements 적재 후보; 실패 시 → validation에 (error_type, value, threshold) 기록.
- **데이터셋 활용**:  
  - **정상 CSV** → Rule 통과만 있는 배치로 “저장 플로우” 테스트.  
  - **이상 시나리오 CSV** → Rule별로 걸리게 만든 행으로 **각 Rule 검증** 및 validation 로그 생성 검증.

### 3.3 클러스터링 (정상 범위 넓게)

- **입력**: 정상 measurements만 (usage, production, equipment_ct, scrap, waste, shift 등 **다변량**).
- **방식**: K-Means 등으로 **정상 구간을 넓게** 클러스터링 → “정상 영역” 정의. (기존 `app/training/pipelines/clustering/` 와 유사하게, 경로만 `get_esg_dummy_dir()` 등으로 ESG 데이터로 교체.)
- **결과**: 정상 영역 밖이면 “이상 후보” → **원인 미상** 또는 **후보·조치 신뢰도** 단계로 넘김.

### 3.4 임계값 조정

- **프로파일/설정**(profile.json 또는 DB)에서 Rule 4·5·6 및 shift별 상·하한 등 **임계치** 보관.
- 클러스터링으로 넓게 잡은 뒤, **디테일**은 이 임계값으로 조정 → UI에서 “정상 범위” 표시·이상 판정과 일치시키기.

### 3.5 다변량 패턴·원인 후보 학습

- **학습 데이터**:  
  - **피처**: usage, production, equipment_ct, scrap, waste, shift, (process, line 원핫 또는 임베딩).  
  - **라벨**: Rule로 명확한 것 → error_type; Rule로 안 잡히는 것 → “원인 미상” 또는 **원인 후보 + 조치** (Notion 예시처럼 신뢰도 %).
- **데이터셋 활용**:  
  - **정상 92~95%** + **Rule별 이상** + **다변량만 이상 2~4%** 구성을 그대로 train/val로 나누어 사용.  
  - scrap/waste 포함해 **효율 지표·이상 패턴** 함께 학습 → “야간 전력 급증 + 설비 미정지” 같은 **패턴**과 **원인 후보 신뢰도** 출력 모델 학습.

### 3.6 PyOD 등 이상치 탐지

- **정상 데이터**로 정상 분포/거리 학습 후, **전체 데이터**에 PyOD(또는 선택한 라이브러리) 적용 → Rule과 무관한 **다변량 이상치** 탐지.
- 탐지된 점은 **클러스터링 정상 영역 밖** + **Rule 미해당**이면 “원인 미상” 또는 **후보·조치 정확도별** UI로 연결.

### 3.7 UI (AI 이상 패턴 분석)

- **입력**: 특정 noticedate·process·line 또는 기간 집계.
- **표시**:  
  - Rule 위반 → 해당 error_type, value, threshold.  
  - Rule 미위반 but 정상 범위 이탈 → **원인 후보 신뢰도 순** + **조치 방향** (즉시 등).  
  - PCF(kg CO₂e) 등은 usage·기간으로 추정해 부가 표시.
- **데이터셋**: measurements + validation 로그 + (학습된 원인 후보 모델 또는 규칙)가 같은 스키마·같은 기간을 쓰면, **지금 문서에서 정한 규모의 데이터**로 전체 플로우를 검증 가능.

## 4. 확장성·재학습 불필요 설계

**원칙**: 공정/라인/지표 추가, Rule 추가, 원인 후보 추가, 정상 범위 변경을 **설정(프로파일·규칙 테이블)** 만으로 처리하고, **모델 재학습 없이** 동작하도록 설계.

### 4.1 스키마 확장성

| 구분 | 설계 | 확장 시 |
|------|------|---------|
| **필수 컬럼** | noticedate, **hour**, process, line, usage, production, equipment_ct, shift, scrap, waste | 시계열·시간대 Rule·이동평균에 `hour` 권장(생성기 출력 기준). 구 데이터 호환 시 `hour` 없으면 일 단위만 가능. |
| **추가 지표** | `extra_metrics` (JSON 또는 key-value 컬럼 1개) | 새 센서·KPI(온도, 습도, OEE 등)는 **스키마 변경 없이** JSON에 추가. Rule/원인 규칙에서 "extra_metrics.xxx" 참조만 추가. |

- 시간 단위 변경(예: 1시간 → 15분)은 **동일 스키마**로 유지하고, 집계 단계(1시간 합산 등)만 별도 레이어에서 처리.

### 4.2 단일 기준 소스 (프로파일·규칙 설정)

- **profile.json** (또는 DB 테이블 `esg_profile`, `esg_rules`) 한 곳에 다음을 둠.
  - **공정·라인별 정상 범위**: usage_min/max, production_min/max, scrap/waste_min/max, day/night 구간 등.
  - **설비 정격·계약 전력·Rule 4·5·6 임계치** (숫자 또는 수식 참조).
  - **Rule 정의 목록**: rule_id, condition_type, threshold_source, threshold_value 등.  
→ **Rule 추가 = 설정에 행 추가**, 코드 수정·재학습 없음.

### 4.3 정상 범위 — 설정 우선, 클러스터링은 보조

- **이상 판정 기준**: “정상 범위”는 **프로파일의 min/max(공정·라인·shift별)** 로 정의.  
  - 클러스터링은 **정상 영역 시각화** 또는 **프로파일 제안용**으로만 사용.  
  - 운영자가 프로파일을 수정(임계치 조정, 구간 확대/축소)하면 **즉시 반영**, 모델 재학습 불필요.
- **신규 데이터 반영**: 최근 정상 데이터로 클러스터를 다시 돌려 “제안 구간”을 만들고, 운영자가 프로파일에 반영할지 결정. 반영 시 **설정만 갱신**하면 됨.

### 4.4 원인 후보·조치 — 규칙 테이블로 확장

- **원인 후보**는 **패턴 → 원인 ID + 신뢰도** 규칙 테이블로 관리.
  - 예: `(shift=night, usage_ratio > 1.5, equipment_ct > 0) → cause_id=CNC_미정지, confidence=0.87`.
  - **새 원인 추가** = 규칙 테이블에 새 행 추가 + 원인 마스터(설명, 조치 방향) 추가. **재학습 없음.**
- 선택적으로 LLM/프롬프트로 “설명 문구”만 생성하고, **판정·신뢰도**는 규칙 테이블 결과를 쓰면, 모델 의존도를 낮출 수 있음.

### 4.5 Rule 엔진

- Rule 체크 로직은 **프로파일/규칙 설정을 읽어서** 동적으로 실행.  
  - **Rule 7, 8 … 추가** 시: 설정에 rule_id와 조건만 추가. 코드는 “설정에 있는 Rule 전부 실행”만 하면 됨.

### 4.6 버전·이력

- **profile.json** (또는 DB)에 **version** 또는 **effective_from** 필드 두고, 변경 이력 관리.  
  - 임계치 조정 후 문제 시 **이전 버전으로 롤백**만 하면 됨. 재학습 불필요.

### 4.7 재학습이 필요 없게 하는 요약

| 항목 | 재학습 없이 확장하는 방법 |
|------|---------------------------|
| **Rule 추가** | 프로파일/규칙 테이블에 rule_id·조건·임계치 추가 |
| **정상 범위 변경** | 프로파일의 min/max·임계치 수정 |
| **공정·라인 추가** | 프로파일에 새 (process, line) 구간 추가; 데이터는 동일 스키마 |
| **새 지표(센서)** | `extra_metrics` 에 넣고, 규칙에서 참조만 추가 |
| **원인 후보 추가** | 원인 마스터 + 패턴→원인 규칙 테이블에 행 추가 |
| **시간 단위 변경** | 동일 스키마, 집계 레이어에서만 단위 처리 |

- **학습 모델**을 쓰는 경우(예: PyOD, 원인 분류)는 **보조**로 두고, **1차 판정·원인 후보**는 설정 기반으로 하면, 운영 변경 시 재학습 없이 대부분 대응 가능.

## 5. 요약

| 항목 | 내용 |
|------|------|
| **규모** | 12~24개월, 1시간 단위, 10 (process, line). 정상 92~95%, Rule별 이상 각 0.5~1%, 다변량만 이상 2~4%. **연 8.5만~9만 행, 2년이면 17만~18만 행.** |
| **손실량·폐기물** | 모든 행에 scrap, waste 포함. 정상은 통상 참고치 범위, 이상은 일부 주입해 다변량·효율 학습에 활용. |
| **출력** | `app/data/esg_dummy/` 아래 measurements(정상/이상), validation 로그, profile.json. 필요 시 paths.py에 `get_esg_dummy_dir()` 추가. |
| **활용** | (1) Rule 엔진 검증 (2) 클러스터링으로 정상 범위 (3) 임계값 조정 (4) 다변량·원인 후보 학습 (5) PyOD 이상치 (6) UI 원인 후보·조치 신뢰도. |
| **확장성·재학습 불필요** | 스키마는 필수 컬럼 + extra_metrics; Rule·정상 범위·원인 후보는 **설정(프로파일·규칙 테이블)** 으로 확장. 새 Rule/원인/공정/지표는 설정만 추가·수정, 모델 재학습 없이 반영. |
| **목적** | **시계열**(추세·주기·다변량)·**이상치**(6 Rule + 다변량 + 라벨)·**예측**(연속 정상 구간·계절성·공정별)까지 **최대한 의미 있게** 쓰이도록 설계. 기준은 `app/data/env_mapping` 참조. |

이 규모와 설계면 **시계열·이상치·예측**과 6가지 Rule, 다변량 패턴, 손실량·폐기물, “원인 미상/후보 신뢰도”를 **의미 있게** 커버하면서, **확장과 운영 변경 시 재학습 없이** 대응할 수 있음.

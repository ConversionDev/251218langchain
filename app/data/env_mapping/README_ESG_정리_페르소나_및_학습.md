# ESG — 정리 탭 (페르소나 · 더미 전략 · 학습 대응)

**용도**: 포트폴리오·발표용으로 **한 파일**에 맥락을 묶어 둠.  
**상세 Rule·수치·파싱**은 `README_ESG_Rule_및_설비기준.md`, 손실·폐기는 `README_배터리_손실량_폐기물_통상참고치.md`, 파이프라인은 `README_ESG_맥락_및_현황.md` §2~3.

## 0. 내 상황에 맞는 한 줄

**목표 스토리**는 EMS·ERP 통합 후 **전력·생산·설비·공정·시간·손실·폐기**를 같이 보고 이상을 판단하는 검증 에이전트이지만, **지금은 실제 EMS/ERP에서 데이터를 가져올 수 없어서**, 그 입력에 **최대한 가깝게** `labeled_slots` 형태의 **합성 슬롯**을 만들고 Rule·복합 로직으로 라벨을 붙였다. **EXaONE SFT**는 그 JSONL에서 **「슬롯 한 줄 → 이상 유형 라벨 한 줄」**만 학습한다(업로드·시스템 A/B 서술은 학습 문맥에 없음).

## 1. 페르소나 (목표 도메인)

| 항목 | 내용 |
|------|------|
| **EMS** | 전력 + 시간 + (위치/계측 맥락) |
| **ERP** | 생산 + 설비 + 공정 정보 |
| **ESG/운영 관점** | 두 축 정보가 다르므로 **통합·해석**이 필요 → **통합된 뷰에서 전력의 의미를 해석하고 이상 여부를 판단** |
| **역할 정의** | **데이터 업로드(또는 적재) 시**, 전력·생산·설비 간 관계를 기반으로 **이상 여부를 자동 판단하는 검증 에이전트** |
| **소스 가정** | EMS → 시스템 A, ERP → 시스템 B (포맷 상이) → **표준 엑셀 템플릿**으로 업로드 데이터를 맞춘다고 가정 |
| **표준 엑셀에 넣는 것(가정)** | 위치 정보는 제외하고, **전력 사용량, 생산량, 설비 가동, 공정·시간, 손실량(Scrap), 폐기물**을 함께 두어 **전력 맥락과 공정 효율을 동시에 해석** 가능하게 구성. **라인·시간별 전력 수요 예측**도 같은 스키마 위에서 확장 가능 |
| **공장 가정** | 믹싱·극판·셀·모듈·팩 등 공정별로 **케이스가 다르고**, 예시 매트릭스와 같이 **10개 공정 라인**(공정×L1/L2 등)을 전제 |

## 2. “가져오면 이미 검증 끝 아닌가?” → 왜 검증이 의미 있나

| 질문 | 정리 |
|------|------|
| **의문** | 시스템에서 끌어온 데이터면 이미 깨끗하지 않나? |
| **현장** | 소스가 깨져 있거나 쓰레기 값·동기 깨짐이 생기는 경우가 있음 → **재검토·정합성 검증**이 별도로 필요 |
| **이 프로젝트에서의 의미** | **“적재된 행이 비즈니스 규칙(전력·생산·설비·시간대)과 맞는가”** 를 자동으로 보는 층이 있음 |

---

## 3. 더미 데이터 — 이상 유형 (Rule 요약)

컬럼 기준 요약. 구현·우선순위·measurements 반영 여부는 `README_ESG_Rule_및_설비기준.md`·`training/pipelines/esg_dummy/README.md` 참고.

| 이상 유형 | 조건(개념) | 한 줄 설명 |
|-----------|------------|------------|
| 1 음수 전력 | `usage < 0` | 센서·수집 오류 등 |
| 2 설비 정격 초과 | `usage > 정격×(1+마진)` | 단일 설비/라인 기준 과다 |
| 3 계약 전력 초과 | 동일 시각 **라인 합산** > 계약 상한 | 공장 단위 수용 가능 전력 초과 |
| 4 생산 대비 전력 이상 | `usage/production` 상한 초과 | 단위 생산당 전력 이상 |
| 5 설비 대비 전력 이상 | `usage/equipment_ct` 상한 초과 | 가동 대수 대비 전력 이상 |
| 6 시간대(교대) 대비 이상 | `usage`가 shift별 정상 밴드 이탈 | 주/야 패턴 대비 이상 |

**Rule 2 vs 5 (의도 구분)**  
- Rule 2: “한 설비 정격 대비 왜 이렇게 많이 쓰나?” → 기계/측정 이슈.  
- Rule 5: “가동 대수 대비 총전력이 왜 이렇게 크나?” → 대수·비효율·데이터 불일치 뉘앙스.

## 4. 참고·근거 데이터 (내가 쓴 방향만 압축)

### 4.1 Rule 1·6 + 시계열 베이스 (약 17~18만 행 스케일)

| 항목 | 내용 |
|------|------|
| **공공 데이터** | **한국전력거래소 시간별 전국 전력수요량**(2021~2025) — 시간대·월·연 패턴 반영 |
| **시간별을 쓰는 이유** | Rule 6(교대/시간대별 정상 범위), 야간 구간 안에서도 **피크 하강 / 기저 / 새벽 반등** 등 미세 패턴이 달라 단일 상·하한만으로는 오탐 가능 → 시간대 참조 필요 |
| **5년치를 보는 이유** | 월·시간대 **비율 테이블**·장기 평균으로 베이스라인 안정화, 특정 2년 편완 완화, Rule 6 임계 설계 근거 |
| **학습·더미는 2년치 중심** | 2년 × 10라인 × 24h × 365 ≈ **17~18만 행** 규모가 현실적; 전년 대비·계절 2회 반복 등 이유 |
| **한계(메모)** | “밤에도 안 떨어지는” 24h 가동·데이터센터·야간 배치 등은 **별도 룰/학습**으로 아직 전부 반영한 것은 아님 |

### 4.2 Rule 2 — 설비 정격 (+10% 마진)

| 항목 | 내용 |
|------|------|
| **근거** | 공개 **공장 단위 표준표**가 없어 **카탈로그 스펙** 활용(코터 MTI/Premier Sols, 건조기 켐시스템/연명 등) |
| **+10%** | 계측 오차(±수%), 기동 순간 피크 → 정격 초과만으로 이상 처리 시 오경보 → **마진 후 이상** |

### 4.3 Rule 3 — 계약 전력 (10라인 시나리오)

| 항목 | 내용 |
|------|------|
| **개념** | 계약 수요(Contract Demand) — 한전 요금·구간과 연계된 **상한** 개념 |
| **참고** | 한전 요금표·KCI 등(공정·설비 참고). PDF 파싱 시 값 오류 가능성 있음 → **수동 `profile_source.json` 등으로 보정** 가능 |
| **시나리오** | 공정×라인별 day 최대 usage 합이 예를 들어 **~4,650 kW**이면 계약은 **110~120%** 대역 등 현실적 상한 가정 → 구현값은 `profile`·생성기 기준 |
| **판정** | **동일 시각(1시간)** 전 라인 `usage` 합 > 계약 상한 → `CONTRACT_EXCEED` |

### 4.4 Rule 4 — 생산 대비 전력

| 항목 | 내용 |
|------|------|
| **난점** | 공시 IR/실측 단위 **공장 내부 kWh/kWh**는 구하기 어려움 |
| **대안** | MDPI 논문·SDI 에너지 리포트 등 **벤치마크·요약** 참고 |
| **현재 구현** | 상수 threshold(예: `usage/production > 39.8`) — 필요 시 **분위수·z-score·EWMA** 등 동적 기준으로 전환 검토 |

### 4.5 Rule 5 — 설비 대비 전력

| 항목 | 내용 |
|------|------|
| **방식** | `(usage/equipment_ct)` 상한 — 실무 형태에 맞춰 상한(예: 95 근처)을 두는 방향 |

### 4.6 Scrap·Waste

| 항목 | 내용 |
|------|------|
| **범위** | LCA·배터리 제조 문헌 기반 **수율 90~97%**, 손실 3~10% 등 통상 구간 |
| **생성** | scrap을 재활용/폐기 경로로 나누는 식으로 공정스럽게 생성 |
| **출처 예** | BatPac, 배터리 폐기물 논문 등 — 상세는 `README_배터리_손실량_폐기물_통상참고치.md` |

## 5. 복합(다변량) 패턴 — 의도만

`MULTIVARIATE_*` 라벨은 **단일 Rule만으로는 안 잡히는 조합**을 의도적으로 만든 것. measurements에는 넣지 않고 라벨·검증 경로로 두는 정책이 있음(파이프라인 README 참고).

| 라벨 | 의도(뉘앙스) |
|------|----------------|
| `MULTIVARIATE_EFFICIENCY_DROP` | 생산은 괜찮은데 단위 생산당 전력이 Rule4 상한에 아주 근접 — 저효율 |
| `MULTIVARIATE_IDLE_POWER` | 생산은 낮은데 전력은 shift 밴드 중상 — 대기·무부하 전력 |
| `MULTIVARIATE_BASE_LOAD` | 생산 0인데 기저 전력만 도는 상황 |
| `MULTIVARIATE_SINGLE_EQUIPMENT_LOW` | 가동 대수는 많은데 대당 전력은 Rule5 대비 낮음 — 부분 부하·병목 |
| `MULTIVARIATE_SCRAP_WASTE_DEVIATION` | 전력·생산은 정상 밴드, 손실·폐기만 통상 상한 초과 |

## 6. EXaONE 학습과의 대응 (정리 탭에서 헷갈리지 않기)

| 구분 | 내용 |
|------|------|
| **학습 입력** | 고정 한국어 지시문 + **파이프(`\|`)로 이은 슬롯 한 줄**(날짜·시간·공정·라인·전력·생산·설비수·교대·스크랩·폐기물) |
| **학습 출력** | `label` 문자열 한 덩어리(`normal`, Rule명, `MULTIVARIATE_*`) |
| **페르소나와의 관계** | 페르소나는 **연동 후 최종 그림**; 지금은 **같은 판단 문제**를 합성 슬롯으로 시뮬레이션 |
| **연동 후** | EMS/ERP → **동일 스키마의 슬롯 한 줄**만 채워 넣으면 같은 태스크로 이어갈 수 있음 |

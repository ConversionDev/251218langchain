# 역량 분류: 학습 모델(EXAONE) vs Gemini 비교

메일 본문을 5대 역량(리더십·기술력·창의성·협업·적응력)으로 분류해 개인 성장이력에 기록하는 기능의 분류기 비교. **동일 프롬프트·동일 입력**으로 직접 파인튜닝한 EXAONE와 관리형 API(Gemini)를 실측했다.

## 실험 설정
- 프롬프트: 운영과 동일 (`email_orchestrator._build_classify_prompt`), JSON 출력(`is_performance`, `competency_labels`).
- 학습 모델: **EXAONE-3.5-7.8B + 자체 역량 SFT 어댑터**(`competency_adapters`), 4-bit NF4, 로컬 GPU(RTX 4060 Ti).
- 비교군: **Gemini 2.5 flash-lite** (관리형 API).
- 측정: 워밍업 후 1회, 생성 256토큰, temperature 0.3.

## 결과 (2026-06-14 실측)

| 입력 메일 | 학습 EXAONE (GPU) | Gemini flash-lite | 정답 라벨 |
|---|---|---|---|
| 킥오프 주도·일정 조율 | 4.1s · `[리더십, 협업]` ✅ | 0.8s · `[리더십, 협업]` ✅ | 리더십, 협업 |
| API p95 850→210ms 개선 | 4.0s · `[협업, 기술력]` ⚠️ | 0.9s · `[기술력]` ✅ | 기술력 |
| 점심 메뉴(비성과) | 3.0s · 성과=False ✅ | 2.1s · 성과=False ✅ | 비성과 |

## 분석
- **정확도**: 둘 다 성과 여부·핵심 역량을 정확히 판별. EXAONE는 한 케이스에서 `협업`을 과태깅(기술 메일에 협업 추가) — 약한 과민. Gemini가 약간 더 깔끔.
- **속도**: 로컬 **GPU에서도 EXAONE 3~4s vs Gemini 0.8~2s**. EXAONE가 2~4배 느림. **프로덕션 배포는 CPU 베어메탈**이라 EXAONE가 훨씬 더 느려짐(수십 초 가능) — 동기 호출 시 발송 UX를 막는 원인.

## 결정 (환경별 분기 + 비동기)
- **로컬/GPU = 학습 EXAONE를 주력**으로 사용. 직접 파인튜닝한 모델이 실제로 분류하는 것을 시연·증명(포트폴리오 핵심).
- **분류는 비동기(백그라운드)** 처리 → 발송은 즉시 끝나고 역량 태깅은 뒤따라 채워짐. EXAONE가 느려도 UX를 막지 않음.
- **Gemini flash-lite는 빠른 대안**으로 확보(속도가 critical하거나 CPU 전용 환경일 때). 추가 의존성·키 없이 기존 `GEMINI_API_KEY` 재사용.
- UI에 분류 모델·역량 라벨을 배지로 노출 → "어떤 모델이 분류했는지"를 사용자가 직접 확인.

> 요약: **정확도는 자체 학습 모델로 충분히 확보**됐고, 속도 제약은 **비동기화 + (필요 시)관리형 API 폴백**이라는 엔지니어링으로 해소. ML 파인튜닝과 프로덕션 운영을 모두 고려한 설계.

## 적용: 작업별 모델 선택 (적재적소)
| 작업 | 성격 | 모델 |
|---|---|---|
| 메일 성과·역량 분류 | 학습된 핵심 판정 | **학습 EXAONE**(비동기) |
| 이력서 Success DNA 점수 | 학습된 핵심 판정 | **학습 EXAONE** |
| 이력서 업로드 폼-채우기 | 단순 필드 추출(빠른 판단) | **Gemini flash-lite**(배포) |
| 스팸 1차 분류 | CPU 배포 제약 | 로컬 LLaMA / 배포 Gemini |

원칙: **학습된 핵심 결과(역량 점수·판정)는 내 파인튜닝 모델, 빠른 판단으로 충분한 단순 작업은 관리형 API.**
